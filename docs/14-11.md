# Retro Fighting Game — Build Plan (Godot 4.x)

A data-driven 2D fighter (Tekken/Mortal Kombat-style loop, 8-bit funny aesthetic).
Single-player: **vs Bot** and **Story Mode**. No online/netcode.

---

## 0. Core design decisions (lock these before coding)

- **Engine:** Godot 4.x, GDScript.
- **Perspective:** 2D side-view fighter. `CharacterBody2D` + `AnimatedSprite2D`.
- **Determinism:** run combat on Godot's `_physics_process` (fixed 60 Hz) so hit timing is consistent.
- **Data-driven characters:** every character = a `CharacterData` resource (`.tres`). Adding a character means creating a resource + sprites, NOT writing new code. This is the most important rule in this doc.
- **Build order:** engine first with **3 characters**, then scale to 15.
- **Specials trigger:** ultimate = energy meter full; comeback move = HP below 20%.

## 2. Fighter architecture (the heart of the game)

### Fighter scene composition (`fighter.tscn`)

```
Fighter (CharacterBody2D)
├── AnimatedSprite2D          # 8-bit animations from CharacterData.sprite_frames
├── StateMachine (Node)       # controls behaviour
├── Hurtbox (Area2D)          # where this fighter can BE hit
├── HitboxSpawner (Node2D)    # attacks spawn Hitbox (Area2D) here, per-frame active
├── HealthComponent (Node)
└── EnergyComponent (Node)
```

### State machine

Every fighter is a finite state machine. Only ONE state is active at a time; it owns
input handling and transitions. States to implement:

`idle → walk_fwd / walk_back → crouch → jump → attack (light/med/heavy) → special → ultimate → block → hitstun → knocked_down → victory / defeat`

Base `state.gd` exposes: `enter()`, `exit()`, `handle_input(inputs)`, `physics_update(delta)`.
The state machine calls the active state each physics frame.

**Why this matters:** state machines prevent the classic fighting-game bug soup ("I can jump while blocking while attacking"). If it's not in the current state's allowed transitions, it can't happen.

### Hitbox / Hurtbox system

- **Hurtbox** (Area2D): always on, on the fighter's body. This is what can be hit.
- **Hitbox** (Area2D): only active during a move's **active frames**. Spawned by the attack state.
- Collision layers:
  - L1 Environment/floor
  - L2 P1 hurtbox, L3 P2 hurtbox
  - L4 P1 hitbox (masks L3), L5 P2 hitbox (masks L2)
- On overlap: hitbox reports `{damage, knockback, hitstun, meter_gain, hit_sfx}` to the victim's HealthComponent, victim → `hitstun` state.

### Frame data (per move)

Real fighters live and die on this. Each move has:

- **startup frames** (windup, not yet dangerous)
- **active frames** (hitbox is live)
- **recovery frames** (can't act — this is what makes whiffing punishable)

Store these in `MoveData` so balancing = editing numbers, not code.

### Input buffer

Keep the last ~10 frames of inputs. Two reasons:

1. Combos feel responsive (press attack slightly early, it still lands).
2. Special-move motions if you want them.

**Recommendation for a "funny, competitive" game:** skip fireball-motion inputs (↓↘→). Use **direction + button** specials (e.g. Back + Heavy = special). Far more accessible, still competitive, way less frustrating. You can add motion inputs later for "pro" characters if you want.

## 3. Character data schema

`resources/character_data.gd`:

```gdscript
class_name CharacterData
extends Resource

@export var id: String
@export var display_name: String
@export var portrait: Texture2D
@export var sprite_frames: SpriteFrames      # all animations

# Stats (this is your balancing lever)
@export var max_health: int = 100
@export var walk_speed: float = 200.0
@export var jump_force: float = 520.0
@export var weight: float = 1.0              # higher = takes less knockback

# Moves (each is a MoveData resource)
@export var light: MoveData
@export var medium: MoveData
@export var heavy: MoveData
@export var special: MoveData
@export var ultimate: MoveData               # usable when energy full
@export var comeback: MoveData               # unlocked when HP < 20%

# Audio / identity
@export var select_sound: AudioStream        # unique per-character select SFX
@export var voice_lines: Array[AudioStream]
```

`resources/move_data.gd`:

```gdscript
class_name MoveData
extends Resource

@export var name: String
@export var animation: String                # animation name in SpriteFrames
@export var damage: int = 8
@export var startup_frames: int = 6
@export var active_frames: int = 3
@export var recovery_frames: int = 10
@export var knockback: Vector2 = Vector2(120, -40)
@export var hitstun_frames: int = 14
@export var meter_gain: int = 8              # energy gained on hit
@export var meter_cost: int = 0             # ultimate/special cost
@export var hit_sfx: AudioStream
```

**Payoff:** 15 characters = 15 `.tres` files. No engine changes. Non-programmers (or you, later) can tune balance by editing exported fields in the Godot inspector.

## 4. Meter / energy / special logic

- **Energy meter** fills from dealing AND taking damage (both `meter_gain`).
- **Ultimate**: enabled only when meter is full; using it drains meter.
- **Comeback move**: a flag flips when `current_hp < 0.2 * max_hp`, unlocking `comeback`. Optional: give it a screen flash + voice line so the player _feels_ the comeback moment.
- All three read from `CharacterData`, so per-character flavor is just data.

## 5. Screens & flow

```
Main Menu ─┬─> Character Select ──> Arena (vs Bot) ──> Results ──> Menu
           └─> Story Mode ──> Story Map ──> Arena (vs monster) ──> ... ──> Boss ──> Results
```

**Character Select (grid):**

- Grid of portraits, all visible on one screen.
- On highlight/select: play that character's `select_sound` (via AudioManager).
- Stores chosen `CharacterData` in `GameManager`, then loads `arena.tscn`.

**Arena:**

- Spawns two `fighter.tscn` instances, injects each with its `CharacterData`.
- One is player-controlled; the other is player 2 OR `bot_controller.gd` (bot/story).
- Round system: best of 3, round timer, health/energy bars, KO detection, win/lose.

## 6. Bot AI

Not machine learning — a simple reactive controller that outputs the _same input struct_ a human would, so it plugs into the exact same fighter code.

Behaviour tiers by difficulty:

- **Easy:** long reaction delay, attacks randomly, rarely blocks.
- **Medium:** approaches, attacks when in range, blocks some incoming hits.
- **Hard:** shorter reaction window, punishes whiffs (attacks during your recovery frames), uses specials.

Difficulty = tuning reaction-delay and probability values. Keep it in data too.

---

## 7. Story mode

- **Story map** = a sequence/graph of nodes (fights). Simplest version: linear list of monster fights ending in a boss.
- Each node references a `CharacterData` (the monster) + optional `StageData`.
- Beating a node unlocks the next; `SaveManager` records progress.
- Boss = a normal fighter with buffed stats + a unique move or two. No special engine work.

---

## 8. Meta systems (later — don't block the fight loop)

- **Save system:** JSON via `SaveManager` — unlocked characters, story progress, daily check-in state.
- **Daily check-in:** on launch, compare today's date to `last_checkin`. If new day, grant reward + advance streak. Pure data + a small UI popup. Build this LAST.

## 11. Gotchas to watch for

- **Facing direction:** flipping the sprite must also flip hitbox positions, or your attacks whiff when you cross up.
- **Hitbox active only during active frames** — a common bug is leaving hitboxes on during recovery, making moves absurdly safe.
- **One hit per move:** track which hurtboxes a hitbox already hit so a single punch doesn't tick damage every frame.
- **Pause the clock, not the physics, correctly:** round-over/hitstop should freeze fighters cleanly (use a global time-scale or per-fighter freeze flag).
- **Balance is data, not code:** if you're editing `.gd` files to tune damage, you did the data layer wrong.
